# Fingerprint Tests

This directory contains all tests for Pivot's automatic code change detection (fingerprinting) system.

## Test Files

- **`test_fingerprint.py`** - Unit tests for fingerprinting functions
- **`test_integration.py`** - End-to-end tests with real Python files on disk
- **`test_change_detection.py`** - Comprehensive change detection behavior tests
- **`test_pydantic_defaults.py`** - Tests for Pydantic default data tracking
- **`test_functools.py`** - Tests for `functools.partial` and `functools.wraps` handling
- **`test_callback_vulnerabilities.py`** - Tests documenting callback detection edge cases
- **`test_determinism.py`** - Cross-process fingerprint stability tests (builtins, default_factory)
- **`test_safe_fingerprinting.py`** - Tests for safe fingerprinting error guards (dynamic name access, unsafe fingerprinting and the run cache)
- **`test_fingerprint_gaps.py`** - CLI regressions for callable class members, dynamic-import spellings, and body imports
- **`test_no_fingerprint.py`** - Worker skip/re-run behavior for `@no_fingerprint()` stages (file-level hashing)
- **`test_fingerprint_properties.py`** - Hypothesis properties over generated stage bodies: fresh-process determinism, formatting insensitivity, one-token sensitivity, and `params.yaml` overrides vs. the run-cache key
- **`test_worker_imports.py`** - A module the program that runs Pivot holds must be the module a stage's worker imports by name (`loaded_source.check_worker_imports`): prediction, confirmation in a new interpreter, the CLI cases that must not fail; and, in-process, the submodules a stage reads through a library package that the walk follows and the coordinator sends (a plain module bound on the package and held in `sys.modules`, not a lazy module subclass such as `six.moves` or a module with no file; with every module that reads it; re-read on a manifest cache hit), and the scan of a `@no_fingerprint` stage's own code for them
- **`test_installed_distribution_fingerprint.py`** - Seven cases of the `dist:` key of an installed library, through the `pivot` CLI (the file holds exactly these seven tests)
- **`test_installed_distributions.py`** - One test per decision of the `dist:` key (hashed files, install forms, reach, dependencies, refusals and their downgrade, a shadowing project file), through the CLI on real installs
- **`test_installed_distributions_project_code.py`** - Project code never meets a rule made for an installed distribution, through the CLI on real installs: a flat setuptools project installed editable (`uv pip install -e`), whose build leaves its `.egg-info` with no RECORD in the root, runs a stage that calls its `@pivot.fingerprint_by_name` helper, or reaches the project's part of a namespace package it shares with a library, with the lock it writes with that `.egg-info` moved out; project code in each kind of path entry outside every `site-packages` and `dist-packages` directory and the interpreter's prefix (the project root, a `src/` directory, a `PYTHONPATH` entry), beside a build's `.egg-info` or a `--target` install that has lost its RECORD, is walked as user code, with no refusal; and a library's checkout in `<venv>/src`, under the prefix, is no project's: a stage that calls a module of it, beside the `.egg-info` its build leaves there with no RECORD, is refused, naming the module's file beside that `.egg-info`, and so is a stage that reaches a namespace package by its top name with a part in the checkout, beside such an `.egg-info` or a `--target` install that has lost its RECORD, naming the part's file
- **`test_installed_distributions_namespace.py`** - The tests of spec requirement N1, through the CLI on real installs: a git install, with its RECORD, of a portion of a namespace package that shares the namespace with an install in `site-packages`, made with `uv pip install --target` into a directory under the venv's prefix that a `.pth` file puts on `sys.path`, or into `site-packages`, and reached by the namespace package's top name: its `dist:` key is in the lock, and one byte changed at a new commit makes the stage stale on that key alone; and the project's part of a package it shares with an installed library (a namespace package, or a regular one whose `__init__` extends its `__path__`), read through the package's name by the stage, a helper module, an output writer's `save` or a deeper namespace package, read as the module `from company import local` bound or only as a function `from company.local import value` bound (its module, which holds a lock no stage reads, is not sent with the stage), held in a `PYTHONPATH` entry and read there by the stage or only inside a lambda, or read only by a module in a `PYTHONPATH` entry (not sent with the stage, which its lock would keep from being pickled): the stage runs in the worker and writes what a plain run writes, and one byte changed in that part makes it stale on that module's `func:` entry alone; a `@no_fingerprint` stage that reads it so in its own code runs, and one whose helper module under the project root alone reads it so fails in the worker, a stated limit
- **`test_installed_distributions_rules.py`** - The pure functions of `pivot.installed_distributions` in-process on plain data (install forms, requirements, RECORD paths, hashed files, digests, the dependency closure, owners, the decision and its refusals), the walk that resolves a RECORD path, and the walk of a reached package's directory; no test starts a process
- **`test_installed_distributions_unlisted.py`** - The refusal of a reached module's file that no RECORD lists beside an install with no RECORD (`installed_distributions.distribution_keys`), in-process on site directories laid out by hand: a module file linked from one path entry into another beside such an install, a module file linked to another file of the path entry that holds one (refused naming the file where Pivot judged it, `fingerprint.judged_file`, there where the import found it), a project file linked into such an install's package (all refused), and a module file beside such an install linked to a file of another path entry that an index RECORD lists, a copy or a link into a cache (not refused); no test starts a process
- **`test_is_library_file.py`** - `fingerprint.is_library_file` in-process on site directories laid out by hand as uv and flit lay them out (a library package linked into a project root, a path entry that is a link to `site-packages`, flit's editable links, and flit's linked module file with the editable install's RECORD kept, user code, or lost, library code: a stated limit) and on chains of links made by hand from a project file (to a file of `site-packages`, copied or linked into a cache: library code in both; to a link an editable install's RECORD lists: user code; to a file outside every library path, and a loop of links: user code; chains of 40 and 41 links); no test starts a process
- **`test_installed_distributions_snapshot.py`** - `installed_distributions.distribution_keys` in-process over real installs, each reached module's origin and located file given as plain data; `fingerprint.add_distribution_keys`; one refusal and two through the registry, whose error names the stage once, first, and keeps all of the text of a refusal that does not start with it; `installed_distributions.listed_by_editable` (only the RECORD of an editable install in a file's own path entry lists it: the finder module uv links for a setuptools editable install, flit's linked module file) and `fingerprint.is_library_file` over files uv links into its cache, a link made by hand in `site-packages` and flit's editable links; the keys of a namespace package, and of a package that holds another install's file, in a venv uv links into its cache; and, on site directories laid out by hand with their files copied or linked into a cache, module and package files linked by hand into `site-packages` (`fingerprint.reached_module_of`), the two layouts compared: a git install there that has lost its RECORD refuses the stage once, naming the file in `site-packages`, alone or beside a project `.egg-info` with no RECORD; a project file linked to a file there that an index RECORD lists or no RECORD lists is not refused beside that `.egg-info` and a local install with no RECORD in the project root, which would refuse it judged where the import found it; a project `.egg-info` in the project root refuses no library file uv links into a cache under the root, which the same `.egg-info` in `site-packages` refuses; a local install with no RECORD in the project root refuses a file uv links into a cache under the root, in the linked layout alone (a stated limit); a project package whose files are linked to a git install's package gets the key of each git install with a file in that package; a file linked from one `site-packages` to a git install's file in another gets its key, or, once its RECORD is lost, one refusal naming the file where its link reaches, as does one linked to a local install's file in a path entry that is no library path; a package file linked to a file another entry's RECORD lists is not refused by the walk of its package
- **`test_installed_distributions_link_mode.py`** - A venv uv builds with `--link-mode symlink` fingerprints as one it copied into (the same lock, `dist:` keys included, no refusal of a library metaclass's `__getattribute__` or of a body import, nothing marked once relinked; the same lock for a module its RECORD does not list); a broken install it holds (a reached library whose RECORD is lost or whose `direct_url.json` is no JSON object, a dependency without RECORD or with such a `direct_url.json`) refuses the stage with the copied venv's `Error:` line, and under unsafe fingerprinting a reached library whose RECORD is lost lets the stage run with the copied venv's warning, kept out of the run cache; and an edit to a checkout installed editable, by flit's `install --symlink` or by uv with the `.pth` file and setuptools' finder module linked into its cache, reruns the stage, as in pivot 0.10.4; CLI only
- **`test_installed_distribution_reach.py`** - The `dist:` key of a git-installed library that a stage reaches through each of six forms (base class, type hint, instance in a value, pivot loader, library stage function, function whose `__module__` is None), one parametrised case per form; CLI only

Loader fingerprint collision tests live in `tests/test_compose.py`.

# Change Detection Matrix

This document exhaustively catalogs what code changes are and are not detected by Pivot's fingerprinting system, with test references.

**Legend:**

- ✅ **Detected** - Change triggers cache miss (correct behavior)
- ❌ **Not Detected** - Change does NOT trigger cache miss (limitation)
- 🚫 **Intentionally Ignored** - By design, change should NOT trigger cache miss
- ⚠️ **Partial** - Some cases detected, others not

---

## 1. Stage Function Itself

| Change Type                     | Detected? | Test Reference                                                        |
| ------------------------------- | --------- | --------------------------------------------------------------------- |
| Function body logic change      | ✅        | `test_change_detection.py::test_function_body_change_causes_miss`     |
| Function argument added/removed | ✅        | `test_change_detection.py::test_function_argument_change_causes_miss` |
| Default argument value change   | ✅        | `test_change_detection.py::test_default_value_change_causes_miss`     |
| Local variable rename           | ✅        | `test_change_detection.py::test_variable_rename_causes_miss`          |
| Parameter name change           | ✅        | `test_fingerprint.py::test_different_variable_names_different_hash`   |
| Type annotation change          | ✅        | `test_change_detection.py::test_type_annotation_change_causes_miss`   |
| Type alias definition change    | ⚠️        | Without `from __future__ import annotations`: alias is in globals, hashed by closure catch-all. With `from __future__`: alias only in string annotation, not captured. |
| Function name change            | 🚫        | `test_change_detection.py::test_function_rename_no_miss`              |
| Docstring change                | 🚫        | `test_change_detection.py::test_docstring_change_no_miss`             |
| Comment change                  | 🚫        | `test_change_detection.py::test_comment_change_no_miss`               |
| Whitespace change               | 🚫        | `test_change_detection.py::test_whitespace_change_no_miss`            |
| Decorator on stage function     | ❌        | **NO TEST** - decorators on the stage itself not tracked              |
| Async vs sync change            | ✅        | `test_change_detection.py::test_async_sync_change_causes_miss`        |

## Design Decisions

1. **Dunder name filtering**: Names starting with `__` are skipped to filter `__name__`, `__file__`, `__doc__`, etc. Single-underscore names like `_private_helper()` are tracked normally.

2. **Library code recorded by name, not hashed**: The walk records stdlib and third-party code by name (`ext:`, `byname:`) and does not hash it, because package version changes should not trigger rebuilds (too sensitive); a stage function a library defines is still hashed by its own body (`self:`), and a loader's `load`, `save` and `empty` by theirs (`loader:`). A distribution installed from git, a local path or a local archive (wheel or sdist), not editable, is the exception, since it can change with no new version: each stage that reaches it, or reaches a library that depends on it, directly or through others, gets a `dist:<name>` key that hashes the distribution's own installed files, read from disk (`fingerprint.add_distribution_keys`, `installed_distributions`; section 6). A reinstall of the same files from another commit, path, installer or venv, or a change of the version alone, keeps the key's value. A package-index install, a remote archive, an editable install and pivot's own distributions get no key.

    Tests: `test_installed_distribution_fingerprint.py` (its seven tests), `test_installed_distributions.py`, `test_installed_distributions_project_code.py`, `test_installed_distributions_rules.py`, `test_installed_distributions_snapshot.py`, `test_installed_distribution_reach.py`

3. **Function name normalization**: Function names are normalized to `"func"` in AST to allow renaming without cache miss.

4. **Docstrings/comments ignored**: These don't affect behavior, so they're stripped from AST.

5. **Imports inside function bodies are walked**: each `import` and `from ... import` statement in a user function's body is resolved (a relative one against the function's package) and what it binds is walked as a module-level import would be. A call `x.import_module(...)` is refused, as on main; other dynamic spellings are left to the worker's stage-import check.

6. **Non-scalar module values are refused**: A stage may capture module-level `bool`, `int`,
   `float`, `str`, `bytes`, and `None` values, a `tuple` or `frozenset` whose members are all
   such scalars (one level deep), and a compiled regex (recorded by full pattern and flags).
   Any other module-level value—including a list, dict, set, a tuple holding a collection or
   object, enum member, frozen model, or class instance—raises `StageDefinitionError`.

7. **Portable bytecode fallback**: When source is unavailable or a function is wrapped,
   `marshal.dumps(__code__)` captures bytecode and constants. Pivot replaces every
   `co_filename` (including nested code objects) before marshalling, so the result is stable
   across checkout paths.

8. **Module-qualified manifest keys**: `func:`, `class:`, `const:`, `schema:`, `partial:`,
   `ext:` and `loader:` keys use the definition or binding module. A value read as
   `settings.NAME` gets the key it would get as a global (`const:settings.FACTOR`,
   `func:settings.helper`, `ext:settings.AGG`). A manifest can therefore
   contain `func:project.alpha.helper` and `func:project.beta.helper` without one overwriting
   the other. A closure cell is keyed under the function that holds it: the stage function's
   own cells under its definition (`const:project.make_stage.<locals>.make.factor`), a local
   helper's cells under the binding it was reached through (`const:project.h2.factor`, with the
   helper at `func:project.h2`), so two closures from one factory keep their own values.

9. **Class body dependency tracking**: When `getclosurevars()` fails on a class, the class body
   is parsed to capture base classes and field annotations. Resolved user-code classes are
   fingerprinted transitively; a third-party base or annotation class is not walked, and its
   module is recorded by name (`byname:`, decision 20); a stdlib or pivot one is ignored.

10. **Pydantic schemas ARE tracked**: Pydantic model classes used in type hints are automatically
    detected and their JSON schemas are hashed via `model_json_schema()` (with titles/descriptions
    stripped to avoid false invalidation from docstring changes). The fingerprint includes a
    module-qualified class-AST key and schema key, e.g.
    `class:project.params.Model` and `schema:project.params.Model`.

    Nested model types are discovered by walking `model_fields` annotations, so changes to nested
    models propagate. A placeholder is inserted before field walking to prevent infinite recursion
    on self-referential models.

    Tests: `test_pydantic_defaults.py::test_pydantic_default_data_captured`,
    `test_pydantic_defaults.py::test_pydantic_class_captured_from_type_hint`,
    `test_pydantic_defaults.py::test_pydantic_default_change_triggers_different_hash`,
    `test_fingerprint.py::test_recursive_pydantic_model_no_infinite_recursion`

11. **`functools.wraps` / `__wrapped__` ARE tracked**: Functions decorated with
    `@functools.wraps` are fingerprinted using portable bytecode hashing. Since
    `inspect.getsource()` follows the `__wrapped__` chain and returns the original function's
    source, Pivot hashes the wrapper's bytecode and still tracks the wrapped function through its
    closure.

12. **`functools.partial` IS tracked**: Partial objects include module-qualified bound-argument
    keys and the underlying user function's definition key. A user function or class bound as
    an argument, directly, inside a nested partial, or inside a list, tuple, set or dict, gets
    the stage-helper walk: its globals, closure values and defaults are tracked, and a
    non-scalar it reads is refused. Loader config fields get the same walk.

    Tests: `test_functools.py::test_function_in_partial_argument_collection_is_walked`,
    `test_manifest_cache_cli.py::test_value_read_by_partial_argument_function_reruns_stage`,
    `test_manifest_cache_cli.py::test_value_read_by_loader_config_function_reruns_stage`,
    `test_manifest_cache_cli.py::test_non_scalar_read_by_bound_function_is_an_error`

13. **StageParams classes fully tracked**: `StageParams` subclasses used in type hints are tracked
    via `_process_type_hint_dependencies()`. The entire class definition is hashed, including
    properties, regular methods, and `ClassVar` declarations.

    Tests: `test_change_detection.py::test_stageparams_property_change_causes_miss`,
    `test_change_detection.py::test_stageparams_method_change_causes_miss`,
    `test_change_detection.py::test_stageparams_class_variable_change_causes_miss`

14. **Builtin types ARE deterministic**: Builtin types (`list`, `dict`, `set`, `tuple`, etc.)
    used as `default_factory` in Pydantic fields are hashed using their qualified name (for
    example, `builtin:list`) rather than `id()`.

    Tests: `test_determinism.py::test_builtin_default_factory_deterministic_across_processes`,
    `test_determinism.py::test_builtin_type_deterministic`

    Set and frozenset values are ordered by their canonical form, not by iteration order,
    which follows `PYTHONHASHSEED`. This covers `StageParams` schema defaults, `default:`
    values, loader config, `functools.partial` arguments, and the params recorded in the
    lock file.

    Tests: `test_determinism.py::test_set_valued_params_are_deterministic_across_hash_seeds`,
    `test_manifest_cache_cli.py::test_set_valued_params_stay_cached_across_processes`

15. **Mutable and nested module collections are refused**: A stage reading a list, dict,
    set, or a tuple or frozenset containing a non-scalar raises `StageDefinitionError` unless
    unsafe fingerprinting is explicitly enabled, in which case Pivot warns instead of
    pretending to track its contents. Exact tuples and frozensets of scalars and compiled
    regexes are recorded by canonical value.

    A method bound to an instance is refused the same way (`apply = Scaler(3).apply`,
    `normal = np.random.default_rng(SEED).normal`): the instance it carries is state no code
    hash records. A method bound to a module, a class, a scalar or a `logging.Logger`, or a
    library module's own export such as `np.random.normal`, is recorded by name instead.

    Tests: `test_integration.py::test_non_scalar_module_attribute_raises`,
    `test_safe_fingerprinting.py::test_immutable_capture_is_tracked_by_value`,
    `test_safe_fingerprinting.py::test_non_scalar_closure_capture_raises`

16. **Manifest cache invalidation is path-scoped**: Watch-mode reloads invalidate only the cached manifests whose source maps include changed paths, leaving unaffected stage manifests intact. Affected stages are recomputed on next fingerprint access and re-cached.

17. **Pivot framework excluded from `is_user_code`**: `fingerprint.is_library_path` decides which resolved paths are library code rather than user code, for a directory by itself and for a file through `fingerprint.is_library_file` (third paragraph): a path in a library location (`installed_distributions.in_library_location`: under the interpreter's prefix, the stdlib or a virtualenv, or in a `site-packages` or `dist-packages` directory), or in one of pivot's own packages. `pivot`'s directory is the one `fingerprint` itself is loaded from. `pivot_tui`'s are the directories the installed pivot-tui distribution records that hold it: its site directory, and each directory a path line of its `.pth` file adds to `sys.path`. They never come from looking the name up on `sys.path`, so a user's own module or package named `pivot_tui` is user code, and an editable install of pivot-tui that records neither (a `.pth` file that installs an import hook or adds a link tree) leaves `pivot_tui` user code. This keeps framework internals (e.g., `StageParams`, `stage`, `Pipeline`, the TUI) out of manifests under an editable install, where neither package is in `site-packages`. A package installed from a source checkout outside the interpreter's prefix is user code. A namespace package is library code when one of its directories is in `site-packages` or `dist-packages` or in one of pivot's own packages; a directory under the interpreter's prefix alone, as pip's checkout of a `pip install -e git+...` package in `<venv>/src`, leaves a namespace the user shares with it user code.

    Library code is recorded by name (decision 2); a distribution installed from git, a local path or a local archive, not editable, also gets a `dist:` key that hashes its installed files. An editable install of a checkout outside the interpreter's prefix and every `site-packages` or `dist-packages` directory is user code, walked like the project's, and gets no `dist:` key, since its `direct_url.json` says editable. pip's checkout of a `pip install -e git+...` package in `<venv>/src` lies under the prefix, so it is library code, and it is editable, so it gets no key either: a change to it is seen only where the walk hashes library code (decision 2). Where its build leaves no `.egg-info` in an entry of `sys.path` (hatchling, flit-core, pdm, poetry-core, uv_build, and setuptools for a flat-layout package, whose editable install loads the checkout through a finder module), its editable distribution's RECORD lists no file of the checkout, so no distribution owns its modules and Pivot follows none of its requirements: a git or local library it requires gets no key through it, and nothing is refused (a stated limit, `docs/architecture/fingerprinting.md`, the Limits of "Libraries Installed from Git or a Local Path"; fix: install it non-editable, or keep the checkout outside the venv). Pivot's own distributions (a RECORD file in one of pivot's packages) get no `dist:` key, and their requirements are not followed. User code never meets a rule made for an installed distribution: `fingerprint.add_distribution_keys` gives `installed_distributions` no module whose file is user code (`is_library_file`), which the walk hashes or the user names by name (`@pivot.fingerprint_by_name`), and of a namespace package only its directories that are library paths (`fingerprint.is_library_path`, each resolved: the rule `is_library_file` gives the files in them, so a directory under the interpreter's prefix outside `site-packages`, as a `--target` install that a `.pth` file puts on `sys.path` or pip's checkout in `<venv>/src`, is keyed and refused as the same install in `site-packages` is, though the rule above for whether a namespace package is itself library code does not count it), so a project's helper and the project's part of a namespace package shared with a library (in the project root, a `src/` directory, a `PYTHONPATH` entry) give no `dist:` key and no refusal, as in pivot 0.10.4.
